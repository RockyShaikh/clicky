Clicky, taken apart

What HeyClicky is, how it decides where to point and draw on your screen, why it can't run on your Claude subscription, and three ways to build the core of it yourself with Claude and Wispr Flow.

Short answers

coderead in the open-source repocompanystated on heyclicky.com or its changeloginferencemy reasoning, not confirmed

  • What is it?

    A Mac app (from Humansongs, Inc., founded by Farza Majeed of buildspace, YC Spring 2026) that you summon with a hotkey. It screenshots your screen, listens to your question, answers out loud, and points or draws on top of whatever app you're in. It has since grown into voice-launched agents, computer use, connectors and persistent named assistants.

  • How does it know what to draw?

    codeIn the open-source v1, it's prompting. The system prompt tells Claude to end each reply with a tag like [POINT:x,y:label:screenN] in the screenshot's pixel space. A regex pulls it out and Swift rescales it onto the display. The accuracy comes from the frontier model's own GUI-grounding training, which Anthropic did (it trained Claude to "count pixels" for computer use). I found no sign Clicky fine-tunes anything, and it has switched model vendors several times, which a custom fine-tune would make painful.

  • Why can't it use my Claude plan?

    Anthropic's terms don't allow it. Pro/Max sign-in is reserved for Claude Code and Anthropic's own apps, and third-party apps may not offer Claude.ai login or route requests through plan credentials. Enforcement started January 2026. Separately, Clicky now runs mostly on OpenAI models (realtime voice and GPT-6 Luna/Sol), so a Claude plan wouldn't cover it anyway.

  • Can I build the core myself?

    Yes, in an evening. Split it into a pen (a click-through overlay that draws shapes from JSON) and a brain (whatever produces the JSON). Your subscription can power the brain two legitimate ways: a hotkey script that calls claude -p, or an MCP server that Claude Desktop or Claude Code calls. Wispr Flow needs no integration: it types into whatever text box has focus.

How v1 works

codeFrom CLAUDE.md, CompanionManager.swift and CompanionScreenCaptureUtility.swift in farzaa/clicky. Each press of the hotkey runs this sequence:

  1. Hold Ctrl+OptionListen-only CGEvent tap catches the chord system-wide.
  2. Stream speechAVAudioEngine → AssemblyAI realtime STT (u3-rt-pro). Apple Speech and OpenAI as fallbacks.
  3. Capture every displayScreenCaptureKit, long edge 1280 px, JPEG q0.8, Clicky's own windows excluded.
  4. Label the images"cursor is on this screen (primary focus)" plus "image dimensions: 1280x831 pixels".
  5. Ask ClaudeSonnet 4.6 default (Opus optional), last 10 exchanges, SSE via a Cloudflare Worker that holds the API keys.
  6. Parse the tagRegex strips [POINT:…] from the end of the reply.
  7. SpeakElevenLabs eleven_flash_v2_5 reads the reply.
  8. Fly and pointFull-screen, non-activating NSPanel; the blue cursor flies a bezier arc to the target.

The overlay is a transparent NSPanel that joins all Spaces and never takes focus. That's why you can "stay still" in your app while it draws on top.

How it knows where to draw

This is the part you asked about. The short version is that "where" is a coordinate the model writes as text, and the rest is bookkeeping.

1. The prompt contract

codeThe voice system prompt in CompanionManager.swift gives Claude a coordinate system, a format and examples. Trimmed:

"the screenshot images are labeled with their pixel dimensions. use those dimensions as the coordinate space. the origin (0,0) is the top-left corner of the image. x increases rightward, y increases downward. format: [POINT:x,y:label] … if pointing wouldn't help, append [POINT:none]."

Then four few-shot examples, such as a Final Cut answer ending in [POINT:1100,42:color inspector] and a second-monitor case ending in :screen2. The parser is one regex anchored to the end of the reply, and the tag is stripped before the text goes to TTS and to conversation history.

2. The coordinate mapping

codeClaude answers in screenshot pixels. Swift clamps, scales to display points, flips Y (AppKit's origin is bottom-left) and adds the display's origin for multi-monitor setups. With the repo's own example sizes:

Claude says (1100, 42) in a 1280 × 831 image Display (points) 1512 × 982 (14" MacBook Pro, default scaling) x = 1100 × 1512/1280 = 1299.4 y = 42 × 982/831 = 49.6 (top-left origin) AppKit y = 982 − 49.6 = 932.4 then + displayFrame.origin

3. The hidden second technique

codeThe repo also ships ElementLocationDetector.swift, which uses Claude's computer-use tool purely as a pointing oracle. It declares a computer_20251124 tool sized to the screenshot (1280×800 for 16:10 Macs), asks Claude to "click on that element," then reads the coordinate from the tool_use block and never clicks anything. Its comment says the tool definition "activates Claude's specialized pixel-counting training, which is significantly more accurate than regular vision API coordinate extraction." In the public version nothing calls this class, so it looks like an experiment that may live on in the private app.

It also documents a classic bug: drawing into an NSImage on a Retina screen silently doubles the pixel count, so the image sent no longer matches the size declared to the model and every coordinate comes back at the wrong scale.

4. Where the skill really comes from

Anthropic's computer-use write-up says: "Training Claude to count pixels accurately was critical." That training is what makes a bare prompt work. Anthropic's vision docs now cover the non-agent case too: "Claude works best with absolute pixel coordinates," and it "does not work well when you ask for normalized coordinates" such as 0–1000 (that's Gemini's convention, so don't copy prompts across vendors).

Verdict: prompting or fine-tuning?

Prompting plus deterministic code, riding on grounding that the model labs trained in. The evidence:

  • The v1 code is a system prompt, a regex and scaling math.
  • The default model moved from Claude Sonnet 4.6 (April) to Claude Fable 5 (July) to GPT-6 Luna (September). A fine-tune doesn't carry across vendors, so a startup that has switched three times is very unlikely to be maintaining one.
  • The quality improvements on the changelog are skill files, a router, walkthrough state and click detection: context and product engineering.

Fine-tuning does exist in this space, just upstream. Open GUI-grounding models (UI-TARS, Microsoft OmniParser, Holo, GTA1) are trained for exactly this, and you'd only need them for a local or free setup.

Why it can't use your Claude subscription

Anthropic's Claude Code legal page spells it out:

"OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." … "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users."

Blocking of plan sign-in in third-party clients began January 9, 2026, and the docs were clarified on February 19, 2026. So a product like HeyClicky has to buy API tokens and resell them inside its $20/$100 plans. And since its realtime voice and default assistant now run on OpenAI, a Claude plan wouldn't cover most of its traffic regardless.

What your plan can legitimately power

  • Claude Code, including headless mode. The same page says the policy doesn't prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription," and claude setup-token exists "for CI pipelines, scripts, or other environments." A personal script that shells out to claude -p fits that.
  • Claude Desktop and Claude Code with your own MCP servers. Local stdio servers are a supported feature, and Claude Code documents that image results from MCP tools are shown to Claude inline.
  • Built-in computer use (research preview, Pro/Max, macOS in the CLI; macOS and Windows in Desktop). It's interactive only, not available with -p, and it acts for you rather than annotating for you.

Two gotchas. If ANTHROPIC_API_KEY is set in the environment, claude -p uses the key and bills the API instead of your plan. And --bare mode skips subscription login entirely. Also, advertised plan limits "assume ordinary, individual usage," so keep it personal. I'm not a lawyer; read the current terms if you plan to share this with anyone.

Build your own

The design that keeps every option open: one small pen process that listens on localhost and draws whatever shapes it receives, and interchangeable brains that send it shapes. Claude via a hotkey is one brain, Claude Desktop via MCP is another, and a person or another script can post shapes too, which covers the "someone writes on my screen later" case.

Path A · start here

Hotkey + claude -p

Stay in your app. Hotkey screenshots, a prompt box takes your Wispr Flow dictation, Claude Code returns JSON shapes, the pen draws them. Runs on your plan.

Path B

MCP "screen pen"

Give Claude Desktop or Claude Code two tools, capture_screen and draw_on_screen. Claude decides when to look and draw, with full conversation memory. Runs on your plan.

Path C

Fork Clicky v1

MIT-licensed Swift app, already polished. Needs your own Anthropic API key (about a cent per question). Lowest latency and closest to the real product.

The shape format (shared by all paths)

~/.screenpen/schema.json
{
  "type": "object",
  "properties": {
    "say":    { "type": "string" },
    "shapes": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "kind": { "type": "string", "enum": ["circle", "arrow", "box", "label"] },
          "x":  { "type": "number" }, "y":  { "type": "number" },
          "x2": { "type": "number" }, "y2": { "type": "number" },
          "r":  { "type": "number" },
          "text": { "type": "string" }
        },
        "required": ["kind", "x", "y"]
      }
    }
  },
  "required": ["say", "shapes"]
}

Conventions: all numbers are pixels in the screenshot the model saw, origin top-left. A circle is centered on (x, y). A box runs from (x, y) to (x2, y2). An arrow points at (x, y) from (x2, y2).

Path A: the pen and the hotkey (Hammerspoon)

Hammerspoon is a free macOS automation app scripted in Lua. Its hs.canvas draws borderless overlay windows, hs.httpserver gives the pen its localhost endpoint, and hs.axuielement reads the accessibility tree for snapping. Grant it Accessibility and Screen Recording. These are starter sketches that I haven't run on a Mac, so expect to debug a line or two.

~/.screenpen/ask.sh · the brain (chmod +x)
#!/bin/bash
# usage: ask.sh <screenshot.png> "<question>"   -> prints shape JSON
set -euo pipefail
unset ANTHROPIC_API_KEY                       # use the subscription login, not API billing
DIR="$HOME/.screenpen"; SHOT="$1"; Q="$2"
sips -Z 1280 "$SHOT" >/dev/null               # long edge -> 1280 px, aspect kept
W=$(sips -g pixelWidth  "$SHOT" | awk '/pixelWidth/{print $2}')
H=$(sips -g pixelHeight "$SHOT" | awk '/pixelHeight/{print $2}')
cd "$DIR"                                     # screenshot lives here, so Read needs no prompt
claude -p "Screenshot file: $SHOT. It is ${W}x${H} pixels, origin top-left.
The user is looking at this screen and asked: \"$Q\"
Read the screenshot, then answer in one or two spoken sentences (field: say)
and give shapes to draw, in this image's pixel coordinates (field: shapes).
Point at the center of the exact control. Use at most 3 shapes.
Return an empty shapes list if nothing on screen is relevant." \
  --model sonnet --max-turns 3 --allowedTools Read \
  --output-format json --json-schema "$(cat "$DIR/schema.json")" \
| jq -c --argjson w "$W" --argjson h "$H" '.structured_output + {imgW: $w, imgH: $h}'
~/.hammerspoon/init.lua · the pen + hotkey
local DIR, ASK = os.getenv("HOME") .. "/.screenpen", os.getenv("HOME") .. "/.screenpen/ask.sh"
local SHOT = DIR .. "/screen.png"
local pen, shotScreen = nil, nil
local voice = hs.speech.new()
local BLUE = { red = 0.12, green = 0.33, blue = 0.94, alpha = 0.95 }

local escKey
local function clearPen()
  if pen then pen:delete(); pen = nil end
  if escKey then escKey:disable() end
end
escKey = hs.hotkey.new({}, "escape", clearPen)

local function arrowHead(x, y, fx, fy)
  local a, L = math.atan(y - fy, x - fx), 16
  return { { x = x - L * math.cos(a - 0.5), y = y - L * math.sin(a - 0.5) }, { x = x, y = y },
           { x = x - L * math.cos(a + 0.5), y = y - L * math.sin(a + 0.5) } }
end

-- result = { say, shapes, imgW, imgH } in screenshot pixels
local function draw(result)
  clearPen()
  local f = (shotScreen or hs.screen.primaryScreen()):fullFrame()   -- points, top-left origin
  local sx, sy = f.w / result.imgW, f.h / result.imgH
  pen = hs.canvas.new(f):level(hs.canvas.windowLevels.overlay)
          :behavior({ "canJoinAllSpaces", "stationary" })
  for _, s in ipairs(result.shapes or {}) do
    local x, y = s.x * sx, s.y * sy
    if s.kind == "circle" then
      pen:appendElements({ type = "circle", action = "stroke", strokeColor = BLUE, strokeWidth = 4,
        center = { x = x, y = y }, radius = (s.r or 28) * sx })
    elseif s.kind == "box" and s.x2 then
      pen:appendElements({ type = "rectangle", action = "stroke", strokeColor = BLUE, strokeWidth = 4,
        roundedRectRadii = { xRadius = 8, yRadius = 8 },
        frame = { x = x, y = y, w = (s.x2 - s.x) * sx, h = (s.y2 - s.y) * sy } })
    elseif s.kind == "arrow" and s.x2 then
      local fx, fy = s.x2 * sx, s.y2 * sy
      pen:appendElements({ type = "segments", action = "stroke", strokeColor = BLUE, strokeWidth = 4,
        coordinates = { { x = fx, y = fy }, { x = x, y = y } } })
      pen:appendElements({ type = "segments", action = "stroke", strokeColor = BLUE, strokeWidth = 4,
        coordinates = arrowHead(x, y, fx, fy) })
    end
    if s.text then
      pen:appendElements({ type = "text", text = s.text, textColor = BLUE, textSize = 18,
        frame = { x = x + 18, y = y + 14, w = 360, h = 26 } })
    end
  end
  pen:canvasMouseEvents(false, false, false, false)   -- keep clicks passing through
  pen:show()
  escKey:enable()                                       -- Esc clears, only while drawn
  if result.say and result.say ~= "" then voice:speak(result.say) end
end

-- the pen also listens locally, so MCP tools, scripts or a person can draw
penServer = hs.httpserver.new(false, false)
penServer:setInterface("localhost")
penServer:setPort(7777)
penServer:setCallback(function(method, path, _, body)
  if method == "POST" and path == "/draw" then
    local ok, result = pcall(hs.json.decode, body)
    if ok and result then
      hs.timer.doAfter(0, function() shotScreen = nil; draw(result) end)
      return "ok", 200, {}
    end
  end
  return "bad request", 400, {}
end)
penServer:start()

-- Ctrl+Option+Space: screenshot first, then ask (dictate with Wispr Flow into the box)
hs.hotkey.bind({ "ctrl", "alt" }, "space", function()
  clearPen()
  shotScreen = hs.mouse.getCurrentScreen()
  shotScreen:snapshot():saveToFile(SHOT)
  hs.focus()
  local button, question = hs.dialog.textPrompt("Ask about your screen", "", "", "Ask", "Cancel")
  if button ~= "Ask" or question == "" then return end
  hs.alert.show("looking…")
  hs.task.new(ASK, function(code, out, err)
    if code ~= 0 then hs.alert.show("screenpen failed: " .. (err or "")); return end
    draw(hs.json.decode(out))
  end, { SHOT, question }):start()
end)

For follow-up questions, add --continue to the claude -p call so it resumes the last conversation in that folder.

Path B: an MCP "screen pen" for Claude Desktop or Claude Code

Same pen, different brain. Claude calls capture_screen, sees the image, and calls draw_on_screen, which posts to the Hammerspoon pen. This uses the Python MCP SDK (pip install "mcp[cli]").

~/.screenpen/screenpen_mcp.py
import json, subprocess, urllib.request
from mcp.server.fastmcp import FastMCP, Image

mcp = FastMCP("screenpen")
SHOT = "/tmp/screenpen.png"
last_size = {"w": 1280, "h": 800}

@mcp.tool()
def capture_screen() -> list:
    """Screenshot of the user's main display, long edge resized to 1280 px.
    Coordinates for draw_on_screen are pixels in THIS image, origin top-left."""
    subprocess.run(["screencapture", "-x", "-m", SHOT], check=True)
    subprocess.run(["sips", "-Z", "1280", SHOT], check=True, capture_output=True)
    out = subprocess.run(["sips", "-g", "pixelWidth", "-g", "pixelHeight", SHOT],
                         capture_output=True, text=True, check=True).stdout.split()
    last_size["w"] = int(out[out.index("pixelWidth:") + 1])
    last_size["h"] = int(out[out.index("pixelHeight:") + 1])
    return [Image(path=SHOT), f"Image is {last_size['w']}x{last_size['h']} px."]

@mcp.tool()
def draw_on_screen(shapes: list[dict], say: str = "") -> str:
    """Draw over the user's screen. Each shape: {kind: circle|arrow|box|label,
    x, y, x2?, y2?, r?, text?} in capture_screen pixel coordinates.
    Circle is centered on x,y; box is x,y to x2,y2; arrow points at x,y from x2,y2."""
    payload = {"shapes": shapes, "say": say, "imgW": last_size["w"], "imgH": last_size["h"]}
    req = urllib.request.Request("http://127.0.0.1:7777/draw", json.dumps(payload).encode(),
                                 {"Content-Type": "application/json"})
    urllib.request.urlopen(req, timeout=5)
    return "Drawn. The user can press Esc to clear it."

if __name__ == "__main__":
    mcp.run()

Register it with Claude Code via claude mcp add screenpen -- python3 ~/.screenpen/screenpen_mcp.py, or add the same command under mcpServers in claude_desktop_config.json. macOS will ask to grant Screen Recording to whichever app launched the server (Claude, or your terminal). Claude Code documents that MCP image results reach the model inline; Desktop is documented to load the same local servers, but I couldn't confirm in its docs that it passes images through the same way, so test that first. This path captures the main display only; use screencapture -D 2 or per-screen snapshots for others.

Path C: fork Clicky v1

  1. Clone farzaa/clicky, deploy the worker/ to Cloudflare with your Anthropic key. You can drop AssemblyAI and ElevenLabs: the repo already has Apple Speech as a transcription provider, and macOS say or AVSpeechSynthesizer can replace TTS.
  2. Swap the regex tag for a JSON shape list (above), so you get circles, boxes and arrows instead of a single point.
  3. Wire in the unused ElementLocationDetector as a second pass for small targets, or add accessibility snapping.
  4. Don't run xcodebuild from the terminal; the repo notes it resets the app's macOS permissions.

Using Wispr Flow instead of their speech stack

Wispr Flow's job is to type cleaned-up speech into whatever text field has focus. That makes it a drop-in replacement for Clicky's AssemblyAI pipeline as long as your brain has a focused text box:

  • Path A: the hotkey opens hs.dialog.textPrompt, which has keyboard focus. Hold your Flow key, speak, release, press Return. Nothing to integrate.
  • Path B: dictate straight into Claude Desktop's input or Claude Code's prompt. Flow's May 2026 update stopped long dictations collapsing into "[Pasted N lines]" in Claude Code and Codex.
  • Order matters. Take the screenshot before the prompt box appears, or exclude your own windows from capture (Clicky does this with SCContentFilter), or the box will cover what you're asking about.
  • Hotkeys. Pick a capture chord that doesn't collide with Flow's push-to-talk key. Flow can toggle hands-free mode with a double-tap, and any non-primary mouse button can trigger dictation, so a mouse button can be your "talk" key.
  • Programmatic route. Wispr does publish a voice API (WebSocket /ws and REST /api), but its docs don't say it's included with a consumer plan, so I wouldn't count on your Flow subscription for it. You don't need it for any of the paths above.
  • Voice out. hs.speech or macOS say is free and instant. Upgrade only if the voice bothers you.

Accuracy recipe

Most "it pointed at the wrong thing" bugs are bookkeeping, not model quality. In rough order of payoff:

  1. Resize the screenshot yourself to a size under the model's limit (1280 on the long edge is safe) and state the exact pixel size in the prompt. Then the image you have is the image the model saw, and coordinates need one scale factor. Anthropic's vision docs recommend exactly this.
  2. Ask for absolute pixel coordinates from Claude. Don't use the 0–1000 normalized convention; Anthropic says Claude does worse with it.
  3. Keep points and pixels straight. Retina screenshots are 2× the display's point size; overlays draw in points. Multi-monitor needs the display's origin added. Hammerspoon uses a top-left origin; raw AppKit uses bottom-left.
  4. Snap to the real control. Before drawing, ask macOS which element sits under the model's point (hs.axuielement.systemElementAtPosition(x, y), then its AXFrame) and draw a box around that frame. Ignore huge frames (that's a container, not a button). Free, and pixel-exact in native apps.
  5. Zoom for small targets. If the first guess lands on a dense toolbar, crop ~400×300 around it from the full-resolution capture, ask again, and add the crop's offset.
  6. One target per step. For multi-step help, draw step 1 only, wait for the user's click inside that rectangle (an hs.eventtap mouse-down listener), re-screenshot, then ask for step 2. That's how you get Clicky's "detects when you click where it told you to."
  7. Add per-app notes. A short Markdown file per app you use often ("in Figma, Auto layout lives in the right panel…") appended to the prompt based on the frontmost app. That's the cheap version of Clicky's skill files.
  8. Exclude your own overlay from screenshots so the model doesn't point at its previous drawing.
